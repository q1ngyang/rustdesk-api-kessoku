# RustDesk API Kessoku v3.0.6 数据库迁移与回退

v3.0.6 将 v3.0.5 数据库从版本 `311` 提升到 `312`。AutoMigrate 会增加持久化客户端类型、
设备身份来源与资料时间戳；随后 v312 迁移只进行保守回填，不删除记录。

## 升级

1. 停止所有 Kessoku 写入实例，对数据库、TOTP 密钥、媒体目录、YAML、签名密钥、Control
   PKI 和当前镜像摘要进行一致性备份，并在隔离环境验证可恢复。
2. 如需发现未登录 Kessoku 的网络设备，先把中心 HBBS 与其 Control Agent 升级到 Starry
   `1.1.16-patch-v1.2.2`；保留原持久数据、身份密钥、本地控制 token、实例 ID、证书和
   服务 JWT 信任，并在 Kessoku 的 `server-control.instances` 中保留该启用实例。实例列表
   为空时只支持已登录设备发现；Starry 配置结构无需修改。
3. 只启动一个 Kessoku v3.0.6 写入实例并等待迁移完成；不得让 v3.0.5 与 v3.0.6 同时
   写入同一个数据库。
4. 确认数据库版本为 `312` 后，再启动其余副本。
5. 分别重启具有登录状态和未登录的 RustDesk 客户端，确认“我的设备”“设备管理”和
   对应地址簿更新主机名、用户名、系统、硬件、UUID、版本、IP 与在线时间。

## 迁移规则

- 旧 Token 会在仍有关联登录日志时回填 `client`；新 Token 直接保存该字段。
- 只有启用用户中尚未过期、未撤销、认证版本一致、ID 规范化后精确匹配且 UUID 非空的
  原生/app Token 才能认领或补全设备。过期、撤销、浏览器、停用用户及旧认证版本会话均
  被忽略。
- 已有非空资料使用最后在线时间初始化资料时间；空白或不完整的占位设备继续保持过期，
  让下一次心跳要求完整上报。
- 设备别名和地址簿个人字段保持不变；身份冲突会记录并跳过，交由管理员明确处理。

## 回退

停止所有 Kessoku 写入实例，恢复升级前完整且相互匹配的数据库、程序、配置与密钥集合。
不要让旧程序读取已经由 v3.0.6 打开的数据库。Starry patch-v1.2.2 可以保留，其新增校验
接口只读，不修改 HBBS 数据库。
