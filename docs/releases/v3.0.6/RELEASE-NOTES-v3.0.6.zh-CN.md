# Kessoku v3.0.6

v3.0.6 完整修复设备发现链路。已登录 RustDesk 客户端只通过当前有效的原生客户端会话
确认归属；同一 RustDesk 网络内未登录账户 API 的客户端，则必须由 Starry 私有 HBBS
注册表精确核对 ID 与设备 UUID 后才能进入设备管理。

## 主要更新

- 新登录的原生客户端会自动进入“我的设备”；未登录账户 API、但已注册到同一 RustDesk
  网络的客户端，在向已配置的 API 服务器上报后自动进入管理员“设备管理”。
- 官方客户端每次启动都会重新核对 CPU、主机名、内存、操作系统、用户名、UUID 和版本，
  资料变化时立即上传；Kessoku 采用完整覆盖更新，空值也会清除旧资料。超过 24 小时未
  收到完整资料时，心跳还会要求客户端重新上报。
- 同一 RustDesk ID 在所有地址簿中的主机名、用户名和平台会随可信资料更新；个人别名、
  密码、标签、RDP 参数和中继偏好保持不变，旧客户端缓存不能覆盖较新的可信资料。
- 登录、心跳、设备资料、连接日志、文件日志和地址簿统一规范化 RustDesk ID，粘贴时的
  空格不会再造成身份分裂。
- Token 持久保存客户端类型。升级只恢复启用用户中未过期、未撤销、认证版本一致的原生
  会话；仅凭历史登录日志不能取得设备归属。
- Starry 校验同时使用 mTLS 与独立的 `starry.peer.verify` 服务 JWT 权限，只返回实例 ID
  和是否精确匹配，不泄露设备资料、密钥、地址或可枚举的注册表。

## 兼容性与升级提示

- 数据库版本为 `312`；迁移只增量更新结构和可信标记，不删除设备、会话、地址簿或日志。
- 如需发现未登录账户 API 的客户端，请先把中心 HBBS 及其 Control Agent 升级到
  [Starry 1.1.16-patch-v1.2.2](https://github.com/q1ngyang/rustdesk-server-starry/releases/tag/1.1.16-patch-v1.2.2)，
  再升级 Kessoku；纯 Relay 节点不提供这项能力。
- Starry 升级期间，已登录客户端仍可通过当前有效的原生会话自动发现。
- 客户端必须配置本 Kessoku API 服务器，并至少启动或发送一次心跳后才能上报；服务端
  不会枚举或主动探测任意桌面。
- 不要原地降级已迁移数据库，应恢复升级前完整且匹配的备份集合。
